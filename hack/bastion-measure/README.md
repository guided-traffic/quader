# What a client's command costs through a Bastion: the measurement W34-E4

A measurement, run once on 2026-11-26 and written down in
[docs/developer/bastion.md](../../docs/developer/bastion.md#what-a-clients-command-costs-through-a-bastion-measured-2026-11-26). It is not
a test and no pipeline runs it. These scripts are here so that it can be run again, for example after a change of the Bastion's
defaults or of a client's version. Nothing here enters the product.

## What it runs

- **The main installation**: the working tree's `quader serve --role all`, on the stores of the worktree's own instance of the UI
  development profile (`make ui-dev-up`: PostgreSQL, Valkey and SeaweedFS in containers), with TLS, no scanner, the Bastion's base
  URL in `server.additional_base_urls` and this machine in `bastions.trusted_proxies`.
- **The Bastion**: the working tree's `quader serve --role bastion`, one replica, the volume backend, no Valkey, every figure at its
  default unless a run names one. Before each cold run it is restarted with an empty cache.
- **The clients**: the format journeys' client images (`quader-e2e-clients`, `-nugetclients`, `-ociclients-docker`, `-ociclients-podman`,
  `-aptclients-debian13`, `-ansibleclients-core217`, each built on the pin of `tools/versions.env` by its `make *-clients-image`
  target), in containers that reach the Bastion's host `packages.e4.test` through the host gateway and trust the profile's CA.
- **The content**: generated by `e4 seed` into local repositories of the project `e4`, readable by anyone: 475 npm packages and the
  lockfile that locks them, 200 NuGet packages and a project that references them, three images (one layer of 4 KiB, 40 layers of
  1 to 2 KiB, eight layers of 128 MiB of random bytes), a Debian suite of six packages, four Ansible collections (one depending on
  the three others), a generic file of 1 MiB, and 768 files of 4 MiB for the overflow attack. Nothing is fetched from a public
  registry.

## How to run it again

```shell
make ui-dev-up                                   # the stores of the worktree's own instance
hack/bastion-measure/setup.sh                    # certificates, configurations, binaries, migrations, registration, tokens
hack/bastion-measure/run.sh main                 # the main installation in the background
E4=.dev/ui-dev-<n>/e4                            # <n>: the instance make ui-dev-up named
$E4/e4 seed -main https://localhost:<main port> -ca $E4/certs/ca.crt -token-file $E4/admin-token \
  -bastion https://packages.e4.test:<bastion port> -out $E4/client   # once; about two minutes, most of it the 1 GiB image and the 3 GiB of the attack
hack/bastion-measure/measure.sh anon             # item 1 without a credential, every command cold and warm (the project is public)
# item 1 with the reader's token: make the project private first (PUT /api/v1/projects/e4/visibility {"level":"private"}), or dotnet
# and APT send no credential at all; then make it public again and run `e4 seed -only repos`, which raises the repositories again
hack/bastion-measure/measure.sh reader
hack/bastion-measure/attack.sh latency idle      # item 3 idle: 600 checks and 600 conditional requests
hack/bastion-measure/attack.sh run spread256 256 120   # items 2 and 3: the attack from 256 addresses for 120 s
hack/bastion-measure/attack.sh run oneaddr 0 90        # the same from one address for 90 s
hack/bastion-measure/shapes.sh stub              # item 4: every client against the four specified error shapes
hack/bastion-measure/shapes.sh bastion           # item 4: every client against the Bastion's refusals as built
hack/bastion-measure/run.sh stop bastion; hack/bastion-measure/run.sh stop bastion2; hack/bastion-measure/run.sh stop main
```

The results are JSON lines under `$E4/results`: per run the tally of `e4 tally` (the request records of both processes whose start lies
in the run's window, and the growth of the Bastion's counters), the window itself, and the client's own output; `e4 tally -paths` lists
every request of a window at both processes. The ports are the instance's scanner ports (`env.sh`), which the measurement's main
installation does not use; the stub and the second replica `bastion2` share two of them, so they never run at once.

| File | What it is |
|---|---|
| `setup.sh` | certificates (one, signed by the profile's CA, for `packages.e4.test`, `stub.e4.test` and `localhost`), `main.yaml`, the binaries, the registration `e4-bastion` and its token, the administrator's token |
| `run.sh` | starts and stops the two processes and runs one client command in its container |
| `measure.sh` | item 1: each command through a cold Bastion and again through the same, now warm Bastion |
| `attack.sh` | items 2 and 3 |
| `shapes.sh` | item 4 |
| [tools/bastionmeasure](../../tools/bastionmeasure) | the Go tool `e4` the scripts build (Go code lives under `tools/`, the tree the architecture tests leave to the repository's own tooling): `seed`, `tally`, `stub` (the four error shapes of the specification), `flood` (the attack) and `latency` |
